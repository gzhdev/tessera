# core-persistence · 设计

## Context

见 `proposal.md` 的 Why。要求见 `specs/persistence/spec.md` 与 `specs/storage-quota/spec.md`。

一个决定实现形态的事实来自设计书 §2.3：每个已激活插件有一个专属 OS 线程，host 函数在该线程上**同步阻塞**执行。这意味着数据库会被多个线程并发访问，且访问是阻塞式的——不能假设单连接串行使用。

## Goals / Non-Goals

**Goals**

- 让六张表的结构与约束在第一次建库时就正确，因为迁移只前滚，改不回去
- 让配额检查足够便宜，因为它出现在每次插件写入的路径上
- 让开发期「推倒重来」与正式迁移是两条互不污染的路径

**Non-Goals**

- 不做配置项的 schema 校验与变更事件（属 `core-host-config`）
- 不做文件交付的 token 生成与写入时机（属 `core-host-storage`）。本 change 只保证保留命名空间的规则被存储层强制
- 不做数据库层面的加密。§11.5 已明确 MVP 不提供加密凭据存储

## Decisions

### D1 · `rusqlite` 的 `bundled` 特性，不用系统 SQLite

**选择**：编译时静态链接 SQLite。

**理由**：桌面应用要在用户机器上开箱即用。依赖系统 SQLite 会引入版本差异（WAL 行为、`RETURNING` 支持等在旧版本上不一致），而这些差异只会在用户机器上暴露。二进制体积增加约 1–2 MB，对桌面应用可忽略。

### D2 · 连接池用 `r2d2` + `r2d2_sqlite`，不自建

**选择**：引入现成连接池。

**理由**：自建 `Mutex<Vec<Connection>>` 看起来简单，但要正确处理连接归还、panic 时的连接回收、池耗尽时的等待策略。这些都是已被解决的问题。`r2d2` 是成熟且轻量的。

**放弃的选项**：每线程一个连接（thread_local）——插件 worker 线程的生命周期与插件绑定，插件反复激活停用会不断创建销毁连接；且宿主自身的 tokio 线程数量不固定。

**连接使用约定**：写操作短小，禁止长事务。WAL 模式下多读一写不互斥，但两个写事务仍会互相阻塞，长事务会把插件 worker 卡住。

### D3 · 迁移脚本编译期嵌入，运行期按序应用

**选择**：`migrations/{NNN}_{name}.sql` 用 `include_str!` 嵌入，运行期读 `schema_migrations` 的最大版本后按序执行未应用的脚本。

**理由**：嵌入保证二进制自带迁移，不依赖安装目录里有 SQL 文件——对桌面分发很重要。编号顺序即应用顺序，简单且可预测。

**每条迁移在单事务内完成**，失败则整条回滚。SQLite 支持 DDL 事务，这一点比某些数据库更友好。

### D4 · 开发期重建与正式迁移严格隔离

**选择**：提供一条独立的「重建数据库」路径（删库 + 从零应用全部迁移），**仅在开发模式下可用**，且与正常启动的迁移路径走不同入口。

**理由**：这是迁移只前滚策略的必然配套。`001_init.sql` 一旦发布就不能再改，但开发期一定会反复调整表结构。若没有明确的重建路径，开发者会直接去改 `001_init.sql`——而这在他自己的机器上「有效」（因为他会顺手删库），在已经应用过旧版 001 的机器上则会静默地留下错误的表结构。

**必须做成显式且刺眼的操作**，不能是「检测到不一致就自动重建」——那种自动化在某天会吃掉真实数据。

### D5 · 配额计数维护增量计数器，不每次 SUM

**选择**：在插件登记记录上维护 `storage_bytes` 与 `storage_keys` 两个计数列，写入/删除时同步更新，与数据写入放在**同一个事务**内。

**理由**：spec 要求每次写入前检查三条配额。若每次都 `SELECT SUM(length(value))`，代价随插件已存数据量线性增长——一个存了 9000 个键的插件每次写入都要全表扫。放在同一事务内保证计数器与实际数据不会分叉。

**放弃的选项**：每次 SUM（热路径上的全表扫）；后台异步对账（引入不一致窗口，而配额是要拒绝写入的硬判断，不能基于陈旧数据）。

**代价**：计数器可能因为外部直接改库而失真。缓解：提供一个重算命令，并在「用户手动清理存储」时顺带重算。

### D6 · 保留命名空间的规则由存储层强制，不靠调用方自觉

**选择**：`plugin_storage` 的写入接口分成两个——面向插件的接口拒绝 `__` 前缀，面向宿主的接口才允许。

**理由**：spec 要求插件写 `__` 前缀被拒。若只有一个接口加个 bool 参数「是否宿主调用」，那个参数早晚会被传错。用两个函数（`set_plugin_key` / `set_reserved_key`）让误用在编译期就不可能发生。

保留命名空间的数据 MUST NOT 计入配额——所以 D5 的计数器更新只发生在面向插件的那条路径上。

### D7 · 内置别名在迁移中插入并标记，不在代码里硬编码

**选择**：`plugin-data` / `workspace` / `temp` 三个内置别名作为 `001_init.sql` 的一部分插入，`builtin = 1`。

**理由**：让「内置别名不可删除」成为数据约束而非代码约束。删除操作检查 `builtin` 标志即可，不需要在代码里维护一份别名黑名单——那份名单会和数据库里的实际内容漂移。

注意 `workspace` 的真实路径在用户选定之前是空的，这是合法状态：别名已注册（所以清单校验第 10 步能通过），但未映射（所以实际访问会失败）。这两种失败要区分开——`E_PERM_UNKNOWN_VDIR` 与「工作目录未选定」是不同的问题。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| `001_init.sql` 发布后发现结构有误 | 只能靠 `002_*.sql` 修正。缓解手段是本 change 尽可能完整地实现 §11.2 的全部表——包括当前 change 用不到的 `plugin_permissions`、`host_settings`，把改动集中在还没发布的时候 |
| 增量计数器与实际数据分叉（D5） | 提供重算命令；用户清理存储时顺带重算；计数更新与数据写入同事务 |
| 开发者绕过重建路径直接改 `001_init.sql`（D4） | 除了提供重建路径，还应在 `001_init.sql` 顶部写明「此文件已冻结，结构变更请新增迁移」 |
| 连接池大小设置不当：过小导致插件 worker 排队，过大导致 SQLite 争用 | 初期设一个保守值并暴露为配置。真实的压力要等 `core-plugin-lifecycle` 之后才能观察到 |

## Migration Plan

`001_init.sql` 建立全部六张表加 `schema_migrations`，并插入三个内置别名。

**本 change 应实现 §11.2 的全部表，即使下游 change 尚未用到它们**——理由见上表第一行。表结构越晚定型，改动成本越高。

回滚：本 change 之前不存在数据库文件，回滚即删除该文件。

## Open Questions

- 数据库文件的确切位置依赖 Tauri 提供的应用数据目录 API，而 `tessera-store` 不能依赖 Tauri（§17.1）。解决方式是路径由调用方传入——这不影响任何 spec 或任务，实现时把 `open(path)` 作为入口即可。
- 备份文件的保留策略（保留几份、何时清理）。当前 spec 只要求「迁移前产生备份」。累积多份备份的清理可以后补，不影响本 change 的验收。
