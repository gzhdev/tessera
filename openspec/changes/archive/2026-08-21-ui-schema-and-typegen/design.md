# ui-schema-and-typegen · 设计

## Context

见 `proposal.md` 的 Why。要求见 `specs/ui-schema/spec.md` 与 `specs/ui-typegen/spec.md`。

这份契约有三个消费方：插件 SDK 的 builder（生成树）、宿主（校验树）、前端（渲染树）。前两者在 Rust 侧，第三者在 TypeScript 侧。设计书 §17.1 的约束 5 要求跨语言契约必须由 Rust 类型生成。

## Goals / Non-Goals

**Goals**

- 让「加一个组件」这件事有唯一的正确顺序，且顺序错了会被工具挡住
- 让校验的产出能表达「局部降级」，而不只是「合法 / 非法」
- 让组件契约的每一次变更在代码评审中以差异的形式可见

**Non-Goals**

- 不实现任何 Vue 组件（属 `ui-component-library`）
- 不做描述树的渲染性能优化。§9.5 已明确 MVP 是全量重绘，增量 diff 是纯宿主侧优化，将来再说
- 不定义视图之外的 UI（设置面板、插件管理界面属宿主自己的界面，不走描述树）

## Decisions

### D1 · TS 类型生成用 `ts-rs`，但先验证再承诺

**选择**：默认用 `ts-rs`；开工第一步是用清单中最复杂的两三个组件（带枚举 props 的、带嵌套结构的）试生成，确认产出可用。

**理由**：`ts-rs` 是直接的 Rust→TS 生成器，产出的类型可读、无中间格式。替代方案 `schemars` + `json-schema-to-typescript` 要经过 JSON Schema 中转，对 Rust 枚举的表达会失真，且引入两段管线。

**放弃的选项**：手写 TS 类型（违反 §17.1 约束 5）；用 JSON Schema 中转（两段管线，失真）。

**退路**：若 `ts-rs` 对某些类型产出不可用，优先调整 Rust 类型的表达方式去迁就生成器，而不是换生成器——组件 props 的形状本来就应该保持简单，生成不出来往往说明类型设计过度了。

### D2 · 每个组件一个 props struct，组件类型是一个标记枚举

**选择**：

```
节点 = { id, type-and-props（标记枚举）, children, on }
```

组件类型与其 props 用同一个枚举表达（`#[serde(tag = "type", content = "props")]` 形式），而不是「一个字符串 type + 一个自由形式的 props map」。

**理由**：spec 要求「属性类型不符被报告」。若 props 是自由 map，类型检查只能在运行期做，且前端拿到的 TS 类型是 `Record<string, unknown>`——静态检查全部落空，D3 里「前端为组件传入契约未定义的属性时类型检查失败」这条要求无法满足。

**代价**：加组件就是加枚举成员，是一次契约变更（这正是我们想要的摩擦）。且组件数量约 30，枚举会比较长——按类别分模块组织。

**与 §9.3 的 JSON 形状一致**：设计书里的示例是 `{"type": "button", "props": {...}}`，正好对应邻接标记枚举，不需要改设计书。

### D3 · 校验返回「降级清单」而非 Result

**选择**：校验函数返回 `ValidationOutcome { tree, degraded: Vec<DegradedNode>, warnings: Vec<Warning> }`，而不是 `Result<Tree, Error>`。

**理由**：spec 明确要求未知类型局部降级、不影响兄弟节点、不拒绝整树。`Result` 表达不了「基本可用但有三个节点要降级」这种状态。让调用方拿到降级清单，它可以决定是渲染占位符（前端）还是记日志（宿主）。

**注意**：这与 `core-plugin-manifest` 的 fail-fast 校验是相反的选择，且是刻意的——清单错了插件不该加载，但界面里一个组件不认识不该让整个面板变空白。

### D4 · 未知类型的检出发生在反序列化之后，不在其中

**选择**：先用一个宽松的中间表示（`type: String` + `props: RawValue`）反序列化整棵树，再逐节点尝试解析为强类型枚举，失败的节点标记为降级。

**理由**：若直接用强类型枚举反序列化，遇到未知 `type` 时 serde 会让**整次反序列化失败**——一个未知节点就毁掉整棵树，与 spec 冲突。两段式反序列化是满足「局部降级」的必要手段。

**代价**：多一次遍历与一次中间分配。描述树规模在几十到几百节点，可忽略。

### D5 · 文件选择组件的载荷形状在契约里定死

**选择**：`file-picker` 的事件 value 是 `{ token, fileName, size }` 三个字段的固定结构，`token` 是不透明字符串。

**理由**：v0.3 决策 B3 把文件选择改成数据交付模型。把形状定死在契约里，插件侧就无法「顺手」期待一个路径字段——它压根不存在于类型中。`token` 声明为不透明，避免插件去解析它的内部结构（比如猜测它对应的存储键格式）。

### D6 · 文本输入组件不设 password 属性，靠类型缺席强制

**选择**：`TextInputProps` 中根本没有 password / masked 字段。

**理由**：v0.3 细则规定凭据统一走配置项。让它在类型中缺席，比在校验里拒绝更彻底——插件作者在 SDK 的 builder 里就找不到这个方法，不会先写了再被拒。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| `ts-rs` 对邻接标记枚举（D2）的 TS 产出不理想 | 这是开工第一步就要验证的（D1）。若产出是可用但丑陋的联合类型，接受；若产出不可用，调整 Rust 侧表达 |
| 30 个组件的 props 契约一次定完，之后删改要走 `CORE_API_LEVEL` +1（§13.2） | 本 change 应刻意保守——宁可少几个组件后续再加（加是兼容的），不要先加了再删（删要 +1）。清单中把握不准的组件优先砍掉 |
| 两段式反序列化（D4）让类型定义与校验逻辑分离，容易出现「类型改了但中间表示没改」 | 中间表示只有两个字段（`type` + 原始 props），与具体组件无关，不随组件增减变化 |
| 生成物一致性检查在开发者本地容易被忽略，直到 CI 才发现 | 提供一条本地命令（如 `cargo xtask gen-types`），并在贡献说明里写明改类型后要跑 |

## Migration Plan

不适用——新增能力。

**推进顺序建议**：先定节点结构与 5–6 个代表性组件（含一个容器类、一个带枚举 props 的、一个数据类如 `table`），把生成管线与 CI 一致性检查跑通，再批量补齐其余组件。先把 30 个组件全定义完再去验证生成管线，是把风险堆到最后。

## Open Questions

- 生成命令的载体（`build.rs` / `cargo xtask` / 独立 bin）。三者都能满足 spec，`build.rs` 会让每次编译都触发生成（可能干扰增量编译），倾向 `cargo xtask`。实现时定，不影响任务拆分。
- 组件属性的默认值如何在 TS 侧表达（可选字段 vs 必填 + 默认）。这影响前端写起来的手感，但不影响契约的可校验性。等 `ui-component-library` 实际写组件时反馈回来再定。
