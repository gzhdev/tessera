# ui-component-library · 设计

## Context

见 `proposal.md` 的 Why。要求见 `specs/ui-renderer/spec.md` 与 `specs/ui-input-model/spec.md`。

前置条件是 `ui-schema-and-typegen` 产出的 TS 类型。本 change 的全部输入都是描述树 JSON，全部输出都是渲染结果与事件——中间不接任何插件、沙箱或 IPC。

一个来自设计书 §9.5 的关键前提：**更新协议是全量重绘**。插件每次 `invalidate` 都会推来一棵完整的新树。这个前提决定了本 change 里最难的问题是输入状态的保持。

## Goals / Non-Goals

**Goals**

- 让「插件推来新树」不会破坏用户正在进行的操作
- 让渲染器的每一条行为都能用手写 fixture 验证，不需要跑通整条插件链路
- 让未知组件的降级是局部的、可诊断的

**Non-Goals**

- 不接 Tauri IPC。事件抛给一个可注入的 handler，由 `core-ui-bridge` 之后接上
- 不做停靠面板容器（属 `ui-panel-system`）
- 不做视图可见性判断与重绘节流（属 `core-ui-bridge`，那是宿主侧的职责）
- 不做宿主自己的界面（设置面板、插件管理器不走描述树）

## Decisions

### D1 · `<UiNode>` 用动态组件分发，映射表从生成的类型派生

**选择**：一个 `<UiNode>` 组件读取节点的 `type`，从一张「组件类型 → Vue 组件」的映射表取出目标组件并动态渲染；容器类组件在自己的模板里递归使用 `<UiNode>` 渲染 children。

映射表的键 SHALL 与生成的 TS 联合类型对齐，使遗漏某个组件类型时类型检查报错。

**理由**：手写一长串 `v-if` 分支既冗长又容易在加组件时漏掉分支。动态组件 + 映射表让「加组件」变成往表里加一项，且类型检查能发现遗漏。

**递归放在容器组件内部而非 `<UiNode>` 内部**：因为不同容器对 children 的布局方式不同（`vstack` 纵向、`grid` 网格、`tabs` 分页），递归点必须由容器自己决定。

### D2 · 未知类型的判断依据是映射表缺失，不是重新校验

**选择**：`<UiNode>` 查映射表未命中即渲染占位符并记 warning，不在前端重新跑一遍 schema 校验。

**理由**：校验已经由 `ui-schema` 在宿主侧做过（`core-ui-bridge` 会在推送前过一遍）。前端再校验一次是重复工作，而且会出现两份校验逻辑漂移的风险。前端只需要处理「我不认识这个类型」这一种情况——而映射表未命中恰好就是这个信号。

### D3 · 输入状态用「本地态优先」模型，不用受控组件

**选择**：文本类输入组件内部持有一个本地值。渲染时的取值规则：

```
节点处于聚焦状态 且 未声明强制取值  →  用本地值（忽略新树的值）
否则                                →  用新树的值，并同步进本地值
```

**理由**：这是 §9.4 那个回环问题的直接解法。受控组件（值完全由 props 驱动）在全量重绘模型下必然导致光标跳动；完全非受控（永不同步）则会让插件无法在合理时机更新输入框。以「是否聚焦」为界是一个用户可预期的规则——**用户正在动的东西不会被抢走，用户没在动的东西会跟着更新**。

**放弃的选项**：以「值是否变化」为界（插件正常更新会被误判为冲突）；用时间戳仲裁（引入时钟依赖，且规则难以向插件作者解释）。

**强制取值的逃生舱**：`props.forceValue` 让插件在确实需要时覆盖（比如「重置」按钮清空表单）。

### D4 · 节流由节点声明，实现在组件内部而非事件总线

**选择**：声明了 `debounce` 的节点，其组件内部对上报做节流；未声明的走 D3 的失焦/回车规则。

**理由**：节流是**按节点**的策略，不是全局的。放在组件内部使不同节点可以有不同间隔，且节点被卸载时节流状态随之销毁——放在外部的事件总线里则要额外管理这些状态的生命周期。

### D5 · fixture 驱动测试，fixture 与组件同目录

**选择**：`src/components/ui/__fixtures__/` 存放描述树样例，测试直接加载这些 JSON 渲染并断言。

**理由**：spec 明确要求「渲染行为可脱离插件独立验证」。把 fixture 当成一等的验收资产而不是测试的附属品，能让它们同时服务三个用途：单元测试、组件开发时的预览、以及将来 `core-ui-bridge` 联调时的对照基准。

**必备 fixture 清单**（对应 spec 的场景）：全组件覆盖树、三层嵌套容器树、含未知类型的树、含重复 id 的树、大表格（几百行）树、含 HTML 注入的 markdown 树。

### D6 · markdown 与 code 组件优先选轻量库，服从受限子集约束

**选择**：markdown 选一个支持子集裁剪、默认转义 HTML 的轻量解析器；code 高亮选支持按语言按需加载的方案。

**理由**：§9.6 已经把 markdown 限定为受限子集（标题、列表、表格、代码块、链接、强调），HTML 一律转义。引入一个全功能 markdown 库然后再关掉大部分功能，是在为不需要的能力付包体积。语法高亮同理——全语言包通常是几百 KB 起。

**HTML 转义必须是默认行为而非配置项**：配置会被误改，默认行为不会。若候选库的默认是解释 HTML，换库而不是加配置。

### D7 · 分两批推进，先骨架后批量

**选择**：第一批只做 `<UiNode>` 分发器 + `vstack` / `hstack` / `text` / `button` / `text-input` / `table` 六个组件，把渲染、递归、事件、输入状态、fixture 测试全跑通；第二批批量补齐其余约 24 个组件。

**理由**：30 个组件如果先全写完再联调，D1/D3 里的机制问题会在第 30 个组件写完后才暴露，那时返工面是全部组件。选的这六个覆盖了全部机制：容器递归、纯展示、无值事件、有值事件与输入状态、结构化载荷事件。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 组件数量大，容易变成一次拖很久看不到进展的批量实现 | D7 的两批推进。第一批结束即可演示完整回路 |
| markdown / code 库带来的包体积 | D6 的选型约束；在第一批就把这两个组件的库选定并测量体积，而不是留到最后 |
| D3 的「聚焦为界」规则在某些组件上不自然（比如 slider 拖动中） | 拖动类组件按 D3 的精神扩展为「交互进行中」而非严格的聚焦。第一批不含此类组件，第二批实现时按同一原则处理 |
| 大表格（几百行）的渲染性能 | 先用 fixture 测量。§9.5 已说明面板节点规模通常在几十到几百，若确实卡顿，虚拟滚动是 `table` 组件内部的优化，不影响契约 |
| 前端测试基建（Vitest + Vue Test Utils）本身的搭建成本被低估 | 放在第一批内完成，作为 D7 第一批的验收条件之一 |

## Migration Plan

不适用——新增能力。

**与 `ui-schema-and-typegen` 的协作**：本 change 实现过程中一定会发现某些 props 契约设计得不好用。这类反馈应回流到 `ui-schema-and-typegen` 改类型再重新生成，**不得在前端本地修补类型**（§17.1 约束 5）。两个 change 在时间上会有重叠，这是正常的。

## Open Questions

- 组件的视觉样式体系（设计 token、暗色主题）尚未定。它不影响任何 spec 中的行为要求，可以先用最朴素的样式把行为跑通，样式统一在第二批或后续单独处理。
- 事件 handler 的注入方式（provide/inject vs props vs store）。三者都能满足「可注入」这一要求，等 `core-ui-bridge` 接入时的实际形状明确后再定更稳妥。
